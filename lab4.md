## Задание 1. Поиск дефектов в тренажёре

Объект тестирования: тренажёр определения типа треугольника (`https://playground.learnqa.ru/puzzle/triangle`).  
При отсутствии спецификации ожидаемое поведение сформулировано на основе предметных знаний (евклидова геометрия) и стандартных требований к веб-формам.

### 1.1. Мини-спецификация

**1. Правила определения типа треугольника:**

| ID | Тип треугольника | Условие |
| :--- | :--- | :--- |
| 1.1 | Равносторонний | Все три стороны равны (`a == b == c`) |
| 1.2 | Равнобедренный | Равны только две из трёх сторон (`a == b`, `a == c` или `b == c`) |
| 1.3 | Разносторонний | Никакие из сторон не равны (`a != b != c`) |

**2. Условие существования треугольника:**
Треугольник существует, если сумма любых двух сторон строго больше третьей:
- (2.1) `a + b > c`;
- (2.2) `a + c > b`;
- (2.3) `b + c > a`.
- (2.4) Вырожденный случай (`a + b == c`) не является треугольником и должен обрабатываться как ошибка существования треугольника.

**3. Требования ко вводу:**

| ID | Параметр | Ожидаемое поведение |
| :--- | :--- | :--- |
| 3.1 | Тип данных | Только целые и дробные числа |
| 3.2 | Знак | Только положительные числа; отрицательные значения — ошибка |
| 3.3 | Ноль | Недопустим (`0` — ошибка, сторона не может быть нулевой) |
| 3.4 | Дробные значения | Допустимы, разделитель — точка (`.`) или запятая (`,`) |
| 3.5 | Пустое поле | Ошибка незаполненного/пустого обязательного поля |
| 3.6 | Нечисловые символы | Ошибка формата заполнения поля, блокировка инъекций (SQL, XSS) |
| 3.7 | Очень большие значения | Обрабатываются без переполнения либо выдают ошибку превышения лимита |
| 3.8 | Пробелы | Допустимы по краям числа, должны автоматически обрезаться (`trim`) |
| 3.9 | Пропуск 1/2/3 полей | Ошибка незаполненного/пустого поля («Задайте все стороны») |
| 3.10 | Порядок ввода | Не важен, поля `A`, `B`, `C` равноправны |

### 3.3. Показательные случаи для тренажёра
1. **Случай А — Низкий Severity (Trivial) при высоком Priority (High):**
   * *Дефект:* Опечатка в тексте на главной кнопке формы — кнопка подписана как «Проверит» вместо «Проверить».
   * *Обоснование:* Влияние на работу алгоритма отсутствует (**Severity = Trivial**), но элемент находится в центре экрана на виду у всех пользователей и портит репутацию продукта, а исправляется за минуту (**Priority = High**).
2. **Случай В — Высокий Severity (Critical) при низком Priority (Low):**
   * *Дефект:* При вводе сверхбольшого числа форма зависает на 5–7 секунд перед выводом ошибки «Числа слишком большие».
   * *Обоснование:* Происходит просадка производительности и блокировка интерфейса (**Severity = Critical**), однако сценарий синтетический и не мешает реальным пользователям в основном потоке (**Priority = Low**).

### 3.4. Разграничение ролей при оценке Severity и Priority
* **Severity (Серьёзность)** — техническая характеристика влияния дефекта на работоспособность системы. Её выставляет **тестировщик**, так как он лучше знает архитектуру, границы компонента и наличие обходных путей.
* **Priority (Приоритет)** — бизнес-характеристика очерёдности исправления. Её выставляет **менеджер продукта (Product Owner / PM)**, так как он оценивает репутационные риски, стоимость простоя и планы релиза.
* **Что произойдёт, если один человек будет ставить оба значения «на глаз»:**
  1. **Смешение измерений:** приоритет будет автоматически копировать серьёзность.
  2. **Потеря критичных для бизнеса мелочей:** косметические баги на главной странице получат низкий приоритет и останутся в продакшене.
  3. **Раздувание приоритетов:** сложные, но редкие краевые баги отвлекут разработчиков от важных бизнес-задач.
  4. **Субъективность:** исчезнет баланс между техническим взглядом QA и бизнес-целями проекта.

def test_partner_def01_turnout_on_exact_boundary(system, voting):
    # Arrange: 4 избирателя, порог явки ровно 50.0%
    voting.registered_voters = ["v1", "v2", "v3", "v4"]

    assert protocol.is_valid is True

def test_partner_def02_multi_mode_exceeds_max_options(system, voting):

    voting.max_options = 2

    protocol = system.count_votes("v-001")

    # Assert: процент должен быть округлён до 33.33
    percent_b = next(r["percent"] for r in protocol.results if r["option"] == "Кандидат Б")
    assert percent_b == 33.33

# Задание 6. Анализ

**1. Какой из трёх типов дефектов оказалось найти труднее всего и почему?**  
Труднее всего оказалось обнаружить **ошибку вычисления (округления)** — как в чужом компоненте (потеря округления процентов до двух знаков в `BallotValidator`), так и в собственном (`ROUND_HALF_DOWN` вместо `ROUND_HALF_UP` для объёма). Чтобы его выявить, требуется целенаправленно подать данные, порождающие бесконечную дробь (`1/3 = 33.333...%`) или пограничную тысячную долю `.005`.

**4. Три условия существования бага и квалификация расхождений в Части А:**  
Баг существует, если выполняется хотя бы одно из трёх условий:
1. Программа не делает того, что явно указано в спецификации.
2. Программа делает то, что явно запрещено в спецификации.
3. Программа работает вопреки разумным ожиданиям пользователя там, где спецификация молчит.  
В Части А официальная спецификация отсутствует, поэтому квалификация полностью опирается на 3-е условие («разумные ожидания»). Если для сторон `0, 0, 0` ожидания однозначны (аксиома геометрии), то для разделителя-запятой (`3,5`) или регистронезависимой фильтрации `<SCRIPT>` представления о «разумном поведении» могут различаться, пока не зафиксирована мини-спецификация.
